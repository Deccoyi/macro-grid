# Changelog (developer)

This file follows the [Keep a Changelog](https://keepachangelog.com/) format. For versioning rules, see [versioning.md](guides/versioning.md). The short, public changelog is [CHANGELOG.md](CHANGELOG.md).

## [Unreleased]

### Changed
- **Pairing is a pairing mode now (protocol behavior, same messages):** a `hello` with a `pin` is accepted only while the editor's Pairing window is open. The window keeps pairing open by polling `GET /api/pairing/qr` (or `/api/pairing/pin`) every 3 s; pairing closes 15 s after the last poll (`PairingService.Lease`) and a PIN still lasts at most 5 minutes. `POST /api/pairing/{qr|pin}/regenerate` opens pairing with a fresh PIN. A PIN is single-use: a successful pairing replaces it. Wrong PINs are limited: 5 from one address block that address for 30 s, doubling per round up to 15 minutes; 20 against one PIN from any address replace the PIN. A client still gets `error` with code `pairing_required` in every case (no new code, so older clients keep working); only the `message` text says which case it is. `PairingService` lost `CurrentPin`, `Verify` and `Regenerate` in favor of `Open`, `Keep` and `TryPair(pin, remoteAddress)`. Device tokens are now generated with `RandomNumberGenerator` (same 32-hex-character format) and compared in fixed time. Tests: `PairingServiceTests`.
- **Releases are checked and carry an SBOM:** `scripts/check-vulnerabilities.ps1` fails on a known vulnerable .NET package (`dotnet list package --vulnerable --include-transitive`) or a production npm package (`npm audit --omit=dev --audit-level=moderate` in `editor/`, `webclient/`, `packages/renderer/`); CI runs it on every pull request (job `vulnerabilities`, plus `dependency-review` for dependencies a pull request adds) and `release.yml` before building. `scripts/sbom.ps1` writes CycloneDX files per part (`dotnet`, `editor`, `deck`, `renderer`), which `release.yml` attaches to the draft release. A fixed vulnerability goes under `### Security` in both changelogs.
- **Device tokens are encrypted on disk (migration):** `devices.json` entries now carry `protectedToken` (Windows DPAPI, current user, base64) instead of `token` when the store has an `ISecretProtector` (the host always does, `DpapiSecretProtector`). A plain file is converted on first load; an entry that cannot be decrypted (another Windows user or PC) is dropped, logged as event 1008, and that device has to pair again. Going back to an older version means pairing all devices again. New package reference `System.Security.Cryptography.ProtectedData` in `MacroGrid.Windows`. Tests: `DeviceStoreTests`.
- **Log files are pruned:** `server-yyyy-MM-dd.log` files older than 14 days are deleted, one day's file stops at 5 MB and all of them together stay under 20 MB (`MacroGrid.Core.Diagnostics.LogRetention`, applied at start and at each new day). Security-relevant lines start with `Security:` and carry event ids 1001-1008 (pairing, removed devices, unreadable device tokens) and 1101-1103 (plugin installed, permissions granted, uninstalled) from `SecurityEvents`; they never contain a PIN or a token. Tests: `LogRetentionTests`.

## [1.0.0] - 2026-09-26
Macro Grid and the plugin SDK now carry **one version**, and it restarts at 1.0.0 (the last separate numbers were server 0.3.2 and SDK 0.4.0). Plugin authors: see "Plugin manifest" below.

### Changed
- **One version, one source:** `<Version>` in `Directory.Build.props` is the only place. `PluginSdk.Version` (now `static string { get; }`, not a `const`) and `ClientHub.ServerVersion` (now the same value) read it from the assembly, so they cannot differ and a plugin no longer inlines the SDK version at compile time. CI fails when either file contains a version literal or a project sets its own `<Version>`. `scripts/publish.ps1` reads `Directory.Build.props`.
- **One tag:** `server-vX.Y.Z` (optionally `-beta`, the GitHub pre-release label) starts both `release.yml` (installer, draft release) and `publish-sdk.yml` (NuGet); the `sdk-v*` tag is no longer used. Both workflows require the tag's `X.Y.Z` to equal `<Version>`.
- **Plugin manifest:** new `macroGrid` field, `MAJOR.MINOR.PATCH` (`"1.3.0"`): the oldest Macro Grid the plugin runs on; it runs on every later version of the same MAJOR (`SemVer.SatisfiesPlatform`). `sdkVersion` and `minServerVersion` are now optional and legacy: when `macroGrid` is absent, `sdkVersion` `^0.4.x` is read as `macroGrid: 1.0.0` (so plugins built for SDK 0.4.0 run on 1.x without a re-release; `PluginLoadContext` already hands them the server's SDK assembly whatever version they reference) and any other `sdkVersion` is incompatible with "must be rebuilt for Macro Grid 1.0.0". `minServerVersion` is ignored. A plugin that must also run on servers older than 1.0.0 can keep the old fields next to `macroGrid`.
- **Compatibility in one place:** `PluginCompatibility.Check` replaces the caret and minimum checks in `PluginManager`, `GET /api/plugin-catalog` and `POST /api/plugin-link/inspect` (`SemVer.SatisfiesCaret` and `SatisfiesMinimum` are gone). Catalog entries and the direct-link response now carry `macroGrid` (and the optional legacy fields) and an `incompatibleReason` the editor shows; the index `formatVersion` may be 1 (`sdkVersion` + `minServerVersion`) or 2 (`macroGrid`). The install cross-check compares `macroGrid` too.
- **Docs:** `docs/guides/versioning.md` describes the single rule; `docs/guides/release.md` is now the one release guide for the server, the SDK, the phone app and the plugins, with the tag table, the order and the signing keys.

## [0.3.2] - 2026-09-25
Plugin SDK 0.4.0 (published to NuGet with the `sdk-v0.4.0` tag) and the plugin distribution feature (Discover). Every plugin's `sdkVersion` range must now satisfy `^0.4.0`.

### Added
- **Badges and update-available (phase 5 of `docs/plans/plugin-distribution-plan.md`, closing out the plan):** `GET /api/plugins` now sends `trust` ("Official" | "ThirdParty" | "Local", from `PluginInstallOriginStore`, defaulting to `Local` for a plugin with no recorded origin — installed from a folder, or before this feature existed) alongside each `LoadedPlugin`. The editor's Installed tab shows that as a badge, and flags a plugin with "Update available" by matching it against whatever Discover last fetched (`PluginCatalogEntryInfo.updateAvailable`) — never a fetch of its own, so Installed never touches the network by itself.
- **Single-plugin direct links (phase 4 of `docs/plans/plugin-distribution-plan.md`):** `POST /api/plugin-link/inspect` reads a pasted repository's root `plugin.json` (or, if it has a `macrogrid-index.json` instead, says so and returns `isMultiPlugin: true` so the editor offers to add it as a source instead) — nothing is downloaded yet. `POST /api/plugin-link/install` resolves the release asset and its `.sha256` from `owner/repo/id/version` (`PluginSourceUrls.SinglePluginPackageUrl`), fetches the hash with new `PluginPackageDownloader.FetchTextAssetAsync`, and runs the normal install pipeline with `PluginTrust.ThirdParty`. `PluginPackageDownloader.DownloadAsync` now accepts an undeclared size (`PluginCatalogVersion.Size == 0`, only method 4 uses this) and falls back to the 100 MB cap instead of requiring an exact match. Editor: "Install from link…" in Discover, same third-party confirmation as an added source. Tests: `PluginPackageDownloaderTests`.
- **Third-party plugin sources (phase 3 of `docs/plans/plugin-distribution-plan.md`):** `PluginSourceStore` persists added multi-plugin repositories in `plugin-sources.json`; `GET/POST /api/plugin-sources` and `DELETE /api/plugin-sources/{id}` manage them (adding one validates it has a `macrogrid-index.json` by fetching it once). `GET /api/plugin-catalog` and `POST /api/plugin-catalog/install` now resolve any saved source in addition to `"official"`; an install from anything but the official source skips signature verification and is recorded with `PluginTrust.ThirdParty`. The editor's Discover tab gained a source selector, an "Add source" prompt, and a third-party confirmation dialog (full-access notice for a C# plugin, the permission list for a JS one) shown before installing from a non-official source. New `PluginSourceUrls.TryParseRepo` accepts a GitHub URL or a bare `owner/repo`. Tests: `PluginSourceStoreTests`, `PluginSourceUrlsRepoParsingTests`.
- **Plugin catalog install (phase 2 of `docs/plans/plugin-distribution-plan.md`):** `MacroGrid.Core.Plugins.Distribution` (`PluginCatalogClient`, `PluginPackageDownloader`, `PluginZip`, `PluginCatalogInstaller`, `PluginInstallOriginStore`, `PluginSigning`) fetches and validates `macrogrid-index.json` from the official plugin repository (`raw.githubusercontent.com`, never the GitHub API), downloads and verifies a release (SHA-256, and its ECDSA P-256 signature against the embedded official public key), safely unzips it to a staging folder, cross-checks the zip's own `plugin.json` against the index entry, and installs it through the existing `PluginManager.InstallFromFolderAsync`. New loopback endpoints `GET /api/plugin-catalog?source=official` and `POST /api/plugin-catalog/install` (`PluginCatalogApi`), and a Discover tab in the editor's Plugins window. The HTTP client is only used when Discover is opened or an install starts, matching the update checker's opt-in-only connection. New optional manifest fields `description`, `author`, `homepage` (additive). Tests: `PluginCatalogClientTests`, `PluginSourceUrlsTests`, `PluginSigningTests`, `PluginZipTests`.
- **Plugin SDK 0.4.0** (`docs/plans/sound-plugin-plan.md`, Phase A): built for the upcoming Sound plugin, but generally usable.
  - `SettingField` gained four kinds: `File` (`FileFilter`, a WinForms filter string) shows a path box with a native Browse
    button (`POST /api/browse/file`, `IUiDialogService.BrowseForFileAsync`); `List` (`ItemFields: SettingField[]`) renders
    repeated rows whose value is a `JsonArray` of `JsonObject` — a row's extra keys outside the schema (a plugin-assigned
    `id`, a computed flag, ...) are preserved across an edit, and a row's own `VisibleWhen` is evaluated against that row's
    values; `Button` (`Command: string`) posts the command and the current form/row values to the settings page's new
    `ISettingsCommandHandler.RunCommandAsync`, showing the returned text; `Notice` is read-only warning text, gated by
    `VisibleWhen` like any other field. `PluginLocalizer.Localize` recurses into `ItemFields`.
  - New `IReleaseAwareAction`: when a `press` binding's handler implements it, `ActionDispatcher.DispatchAsync` calls
    `ReleaseAsync` on the `release` event, before that event's own bindings run (a failing `ReleaseAsync` is collected the
    same way a failing `ExecuteAsync` is). Lets an action know its widget button was let go, e.g. "play while held". Tests:
    `ActionDispatcherTests`.
  - New optional manifest field `icon` (a path relative to the plugin folder, `.svg` or `.png`, at most 100 KB): the
    editor's Plugins window shows it next to the plugin's name (`GET /api/plugins/{id}/icon`, `LoadedPlugin.HasIcon`); an
    invalid or oversized icon is silently treated as absent (cosmetic, never fails the plugin's own load). Additive —
    older hosts ignore it. Tests: `PluginManagerTests`.
  - Every plugin's `sdkVersion` range must now satisfy `^0.4.0`; the bundled OBS and PLCIcons plugins are updated in the
    plugin repository (`macro-grid-plugin`) separately.

## [0.3.1] - 2026-09-25
0.3.0 was published and withdrawn the same day (set back to a draft; its tag stays) because of the first fix below; 0.3.1 replaces it and has the same content.

### Fixed
- **The app came back elevated after an update:** when the app started the setup itself (an administrator prompt from another process), neither a plain `[Run]` entry nor a `postinstall` entry with `runasoriginaluser` started it again as the person; only a setup started from Explorer did. The update run now starts `explorer.exe "<app>\MacroGrid.exe"` (`postinstall`, `IsUpdateRun`), which uses the person's normal token. That passes no `--updated`, so `StartupPolicy.WasUpdated(args, lastRunVersion, currentVersion)` also compares the version that ran last (`UpdateState.LastRunVersion`, written at every start) with the current one; the argument still counts. Tests: `StartupPolicyTests`.
- **Update download deleted right after it finished:** `UpdateInstaller` cleaned the downloads folder after each download, and `DownloadedInstallers.CleanUp` kept the newest version there, so a newer leftover (a made-up test release) made it delete the installer that had just been fetched; the setup then failed to start with "cannot find the file". `CleanUp` takes the version just downloaded (`keep`) and always keeps that one. Test: `The_version_that_was_just_downloaded_stays_even_when_a_newer_leftover_exists`.
- **Website workflow failed when a release was published:** a release runs the workflow on its tag, and the `github-pages` environment accepts only `main`, so the download page was not refreshed. A release now only starts a manual run of the workflow on `main` (job `refresh`); build and deploy skip the release event.

## [0.2.1] - 2026-09-24
### Changed
- **Localized catalog text and window titles:** the server now sends language-neutral English text for built-in and OBS action names, descriptions, variable descriptions and categories (`/api/actions`, `/api/variables/catalog`, tool window titles). The editor translates them by stable id (action type, variable name, category id) in `i18n/catalogText.ts` (`useCatalogText`) and falls back to the server text, so a plugin without an entry still shows its own description. Window titles come from `document.title` (`useDocumentTitle`); `WebViewEnvironment.AttachAsync` copies it into the native title bar (`followDocumentTitle`, off for plugin settings windows, which are titled with the plugin name). Not yet localized: setting field labels/descriptions, the tray menu and native file dialogs.
- **Fixed (installed build):** WebView2 needs a user data folder it can write to; the default one next to the exe is under Program Files after an install and failed with `E_ACCESSDENIED` (0x80070005). `WebViewEnvironment.AttachAsync` (used by the editor and every tool window) now tries `%LocalAppData%\MacroGrid\WebView2`, then `%AppData%\MacroGrid\WebView2`, then the temp folder, and the first that starts wins. When none does, the error dialog lists every folder with its exception and HRESULT and the same text goes to `%TEMP%\MacroGrid-webview-error.txt`. Found on a clean domain-joined PC where the first attempt (LocalAppData only) still failed.
- **Fixed (single-file publish):** `PluginLoadContext` hands a plugin the host's own copy of `MacroGrid.Plugin.Abstractions` whatever assembly version the plugin was built against. Before, a plugin built against SDK 0.3.0 failed to load on a server with SDK 0.3.1 in the single-file build (`FileNotFoundException` for version 0.3.0.0). Compatibility stays decided by the manifest's `sdkVersion` range. Covered by `PluginLoadContextTests`.
- **Plugin SDK 0.3.1:** package README now opens with an AI notice (AI-generated, unreviewed code, no warranty, use at your own risk); no code change.
- **Installer:** bundles Microsoft's WebView2 bootstrapper (downloaded and signature-checked by `build-installer.ps1`, kept in git-ignored `artifacts/redist`) and runs it silently only when the runtime is missing, detected in the Inno Setup `[Code]` section through the runtime's registry key. Fixes a clean Windows install that could not open the editor window.
- **Plugins window:** `PluginsWindow` mounts its own `DialogHost`. It is a separate native window (`?window=plugins`), and the host in `App.tsx` does not exist there, so `confirmAsync` for "Remove" never resolved.
- **Product renamed from "Macro Station" to "Macro Grid":** namespaces, projects, assemblies (`MacroGrid.*`), solution, installer script/exe, repo names (`macro-grid`, `macro-grid-client`, `macro-grid-plugin`) and the npm package names were renamed. Migration remark: the user-data folder changed from `%APPDATA%\MacroStation` to `%APPDATA%\MacroGrid` and the browser-deck localStorage keys from `macro-station.*` to `macro-grid.*`; there is no migration code because there are no users yet (move the old folder by hand on a dev machine if needed). The SDK assembly is now `MacroGrid.Plugin.Abstractions`.

### Added
- **Default language and plugin translations:** `AppPreferences.Language` defaults to the Windows display language (`AppLanguage.SystemDefault`), `AppLanguage.Current` follows the stored preference for server-made texts (boolean words in templates, the sample profile). New `PluginLocalizer` translates action, category, variable, form-label, option-error, icon-pack, status and plugin names per plugin: `plugin.json` gets `defaultLanguage` (default `en`) and the plugin may ship `locales/<language>.json` (default-language text -> translation); a missing language or entry falls back to the text as written. `VariableCatalog.Add(source, pluginId)` remembers the owner. The native shell texts (tray menu, balloon, app picker, start-up messages) live in `HostText` and follow the preference live via `PreferencesStore.Changed`. Server API errors and log messages are English. Covered by the existing tests (boolean words and sample profile no longer depend on the machine language).
- **Startup modes:** `AppPreferences.LaunchMode` (`window` default, when the person starts the app) and `AutostartMode` (`tray` default, when Windows starts it). `StartupPolicy.ShouldOpenEditor` decides from the command-line argument `--autostart`, which the per-user `Run` value carries (`AutostartService` writes it; the installer's task writes the same). `TrayContext` opens the editor when the policy says so. Unit tests in `StartupPolicyTests`.
- **Autostart switch:** `GET/PUT /api/system/autostart` read and write the `Run` value (`AutostartService` in `MacroGrid.Windows`), shown as a checkbox in Preferences, General.
- **Legal texts in the app:** `LegalDocuments` reads `license-agreement.txt`, `LICENSE`, `THIRD_PARTY_NOTICES.md` and `licenses/*` next to the exe; `GET /api/legal` and `GET /api/legal/library/{name}` (the name must be an existing folder, nothing else is read). The Help window has About, User Agreement and Third-Party Licenses. `POST /api/windows/help?tab=about|agreement|licenses` opens a tab. `scripts/publish.ps1` copies the agreement into the publish folder.
- **Installer:** `LicenseFile` (`installer/license-agreement.txt`, must be accepted), desktop shortcut ticked by default, firewall rule for `domain,private`, `taskkill` of a running instance before install and uninstall, `[UninstallDelete]` of the program folder.
- **Tool windows block the editor:** `ToolWindow` shows itself with `Owner` = the editor window and sets `Enabled = false` on the editor while any tool window is open (counter; released in `FormClosing` so the editor comes to the front). Clicking the editor plays the Windows warning sound. No `ShowDialog`, so no nested message loop inside the API call that opens the window.
- **Automatic profile switching based on the active window (opt-in):** see `docs/design/auto-profile-switch.md`. `AppMatches` (process name + optional title filter) was added to the profile model. `MacroGrid.Windows.ForegroundWindowMonitor` (`SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`, event-driven, no polling) and `AutoProfileSwitcher` in Core (`IHostedService`) drive each session's own stack-based `AutoSwitchState`. When a defined window comes to the foreground, the session switches to that profile. When an undefined window gains focus (focus loss) or the app closes, it returns to the manually chosen profile. If the stack runs empty, `ProfileResolver.ResolveDefault` takes over (device assignment → `AppPreferences.DefaultProfileId` → first profile). Each device opts in with `PairedDevice.FollowActiveWindow`. The drawer lock (`PairedDevice.AutoSwitchLocked`, new `profile.lock` message) pauses auto-switching but leaves manual switching available. New endpoints: `GET /api/system/windows`, `PUT /api/devices/{id}/follow-window`. `profiles.list` now carries `autoSwitch: {enabled, locked}`. Editor: a rule list opened by a window icon in the profile panel (pick from running apps or type an exe name), a per-device "Follow active window" switch in Pairing, and a default-profile picker under the "Profiles" category in Preferences. The stack, lock and default logic of `AutoSwitchState` is covered by unit tests (`AutoSwitchStateTests`); verified end to end with real OS foreground events (rule window ↔ another window). The drawer lock is now a switch with a lock icon.
- **A failed widget action is now a visible warning:** it used to be written only to the server log file (for example a button bound to a deleted OBS scene). `ActionDispatcher.DispatchAsync` now collects error messages and `ClientHub` forwards them to two places: the editor status bar as a `core.actionError` warning (`StatusBar.tsx` is already generic, so no extra code was needed), and the device that triggered the action as an `error`/`action_failed` envelope, shown in both the web/browser client (`webclient/`, red toast, 4 s) and the real Android app (`macro-grid-client`, same toast pattern). Verified end to end with real OBS and a real device (USB `adb`).
- **Plugin uninstall:** `DELETE /api/plugins/{id}` (`ServerApp.cs`) deletes the `%AppData%/MacroGrid/plugins/<id>/` folder. The plugin is unloaded first (see "Plugin hot loading" below); if a file is still in use anyway, an `.uninstall` marker file is left and `PluginManager` deletes marked folders on the next start before loading anything. A Remove button (`PluginsWindow.tsx`, `Trash2` icon) was added to each row of the editor's "Plugins" window. Because it is destructive, it asks for confirmation through `confirmAsync` (the app-styled confirm in `dialogStore.ts`, not the native `confirm()`).

- **JS plugin runtime (`docs/design/js-plugin-runtime.md`):** `kind: "js"` plugins run in a Jint sandbox. `JsPlugin` (`Core/Plugins/Js`) implements `IPlugin`, so it goes through the same `PluginManager` pipeline as a C# plugin (registrations, hot load, unload, uninstall); it runs on its own thread with a one-job-at-a-time queue and per-call limits (`JsPluginLimits`: 2 s, 32 MB, 2M statements, recursion 100, 20 timers, HTTP 5 s / 1 MB). The engine gets no CLR access; the script sees only a frozen `host` object built from delegates that the bootstrap script captures and removes from the global scope. Every host call checks the approved permissions (`JsPermissions`: `variables`, `actions`, `input`, `http:<host>:<port>`); variable names and action types must start with the plugin id; HTTP only to approved host:port, no redirects. Approvals are kept per plugin in `plugin-permissions.json` (`PluginPermissionStore`) and are for an exact set: a plugin that asks for more waits again (`PluginLoadStatus.NeedsApproval`, `LoadedPlugin.PendingPermissions`). New endpoint `POST /api/plugins/{id}/approve`; the editor's Plugins window lists the permissions and has an allow-and-enable button. A plugin that fails 5 times in a row is switched off (`PluginManager.DisableAsync`). `PluginManager` gained `ApproveAsync` and takes the permission store and `IInputService`; uninstall forgets the approval. `Jint 4.16.3` was added to `MacroGrid.Core`. Example plugin: `macro-grid-plugin/HelloJs/`. Tests: `JsPluginTests` (sandbox: no CLR, frozen host, namespaces, endless loop, memory, recursion, switch-off, timers, HTTP, input, settings) and JS cases in `PluginManagerTests`.
- **Release packaging (`docs/guides/release.md`):** `scripts/publish.ps1` builds the editor and publishes a self-contained single-file `MacroGrid.exe` (compressed, about 62 MB, with `wwwroot` beside it; version read from `ClientHub.ServerVersion`, WebView2 reference XML files removed) into `artifacts/server`. `installer/MacroGrid.iss` and `installer/build-installer.ps1` wrap it in an Inno Setup installer: Start menu entry, optional desktop shortcut, optional per-user autostart, inbound firewall rule for TCP 9820 on private networks (removed on uninstall), running server closed before an upgrade, `%AppData%/MacroGrid` kept on uninstall. The published exe was smoke-tested (starts, serves `/api/plugins` and the editor); the installer script itself was not compiled because Inno Setup is not installed on the development machine.
- **`.msprofile` export and import:** `ProfilePackage` (`Core/Profiles`) writes and reads a zip with `manifest.json` (format version, profile name, export time, server version, the plugins the profile's actions need with the action types used) and `profile.json`. Icons and images stay inside `profile.json` as the `data:` values the profile already holds, so a package is self-contained; there are no separate asset entries (yet no sounds exist either). Reading is defensive: only the two known entries are read, capped at 64 MB with the read itself bounded, the profile must pass `ProfileValidator`, a package with a newer `formatVersion` is refused with a clear message, and a plain profile JSON (the older export) is still accepted, just without a manifest. `POST /api/browse/export-profile` now takes the profile and writes a package; `POST /api/browse/import-profile` returns the profile plus `missingPlugins` (from the manifest, checked against loaded plugins by `PluginManager.MissingPlugins`) and `unknownActionTypes` (bound action types nothing provides). `IUiDialogService` open/save are now byte-based and take a file filter (`OpenFileAsync`, `SaveFileAsync`; the JSON-only versions were removed). The editor's File menu exports `.msprofile`, imports `.msprofile` or `.json`, shows the server's reason when a file is unusable and warns about missing plugins after an import. Tests: `ProfilePackageTests`, `PluginManagerTests`.
- **Widget text and icon dynamization:** `Widget.Dynamic["text"]` and `["style.icon"]` are now honored. `DynamicText` (`Core/Variables`) picks the text template (first matching case, else default, else the static text) and renders it, so a rule result may contain `{variables}`; `WidgetStateService` uses it for the initial push and for live updates (recomputed when a variable in the conditions or in any candidate template changes) and always pushes the text of a dynamized widget. `style.icon` was added to `DynamizableProperties`; the icon travels in the `widget.state` style, as an `asset:<hash>` reference for clients with the `assets` capability (`LayoutSender.ForClient`, `AssetStore.ExternalizeValue`). Editor: `DynamizeModal` gained the `"text"` and `"icon"` result kinds (the icon kind reuses `IconPicker`, baked with the widget's text color; an empty case result means no icon), `TextFields` got the lightning-bolt on the text and icon labels, and the canvas previews both (`evaluateWidgetDynamicText`). Both renderer copies accept `icon` in `liveStyle` / `WidgetState.style`. Tests: `DynamicTextTests`.
- **Plugin hot loading:** `PluginManager` (`Core/Plugins`, hosted service registered after `VariableProviderHost`) replaces the one-shot `PluginLoader`. Plugins are installed, reloaded (`POST /api/plugins/{id}/reload`) and uninstalled while the server runs; `POST /api/plugins/install` loads the plugin immediately and replaces an existing id (its own files such as `settings.json` are kept). Registrations are applied to now-dynamic registries (`ActionDispatcher.Register/Unregister`, `VariableCatalog.Add/Remove`, `VariableProviderHost.StartOwned/StopOwnerAsync`, `PluginStatusRegistry.RemovePlugin`) and taken back out on unload; variables a plugin set are removed through `TrackingVariableStore`; the plugin instance and everything it registered is disposed if it implements `IDisposable`/`IAsyncDisposable`. An action type clash fails the whole plugin and rolls back. Plugin assemblies are loaded from memory (`PluginLoadContext.LoadPluginAssembly`) so files are never locked (`Assembly.Location` is empty inside a plugin). The editor's Plugins window has reload and no longer asks for a restart; the main editor refetches actions, variable catalog and icon packs on window focus. Tests: `PluginManagerTests` (replaces `PluginLoaderTests`). See `docs/design/layout-patch-and-assets.md`.
- **`layout.patch`:** a saved edit reaches a client that announced the `layout.patch` capability as only the changed widgets (`LayoutDiff`, per-session baseline in `ClientSession.SentLayout`, `LayoutSender.SendUpdateAsync`); nothing is sent when nothing the client renders changed. `WidgetStateService.BroadcastProfileAsync` clears the sent-state cache only for the changed widgets and re-sends their live state. Other clients (the browser client) still get `layout.full`.
- **Cached assets:** with the `assets` capability, `data:` values of 200+ characters in a layout become `asset:<hash>` references (`AssetStore`, SHA-256 based, LRU); the client fetches missing ones with `asset.get` and gets `asset` replies. `hello` gained `capabilities` (`ClientCapabilities`). All layout sends go through `LayoutSender`. Tests: `LayoutDiffTests`, `AssetStoreTests`, `LayoutSenderTests`.
